# Operational Event Schema

All events are append-only. Never update — only append.

## Event Types

| event_type | Trigger | Meaning |
|------------|---------|---------|
| `started` | Worker begins processing batch | Batch entered this station |
| `completed` | Worker finishes batch at station | Batch ready for next station |
| `issue_flagged` | Worker taps issue button | Problem at station, needs attention |
| `skipped` | Station bypassed for this batch | Batch moved to next station directly |

## Payload

```json
{
  "batch_id": "uuid",
  "station_id": "uuid",
  "event_type": "started | completed | issue_flagged | skipped",
  "device_id": "string — physical device identifier",
  "idempotency_key": "uuid-v4 — generated by device, prevents duplicate on retry",
  "timestamp": "ISO 8601 with timezone — device clock time",
  "metadata": {
    "asr_confidence": 0.94,     // present if voice-triggered
    "issue_code": "STAIN_HEAVY" // present if event_type = issue_flagged
  }
}
```

## Idempotency

The `idempotency_key` is generated on the device at event creation time.
If the same key arrives twice (e.g. after retry), the second write returns `409 Conflict` — treated as success by the sync engine.

This prevents duplicate events when:
- Wi-Fi dropped after device sent but before ACK received
- Device rebooted mid-sync
- User double-tapped button
